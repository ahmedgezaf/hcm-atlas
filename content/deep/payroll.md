Payroll in Oracle is a chain of objects, each depending on the one before it. A consultant who can recite the chain and explain what breaks when a link is missing can debug most payroll problems without opening a log. The chain runs: element → element eligibility → element entry → payroll run → balance → prepayment → payment → costing.

The chain is worth learning in both directions. Forwards, it is how a payroll is built: define the thing, decide who may have it, give it to someone, run, accumulate, distribute, pay, account. Backwards, it is how a payroll is debugged, and that is the direction a consultant uses more often. A payment is wrong, so look at the prepayment. The prepayment is wrong, so look at the run result. The run result is wrong, so look at the entry. The entry is missing, so look at eligibility. Eligibility is fine, so look at the element. Six questions, in order, and almost every payroll incident is answered before the sixth.

## Defining what can be paid

An **element** is the definition of a single thing that can appear on a payslip: a salary, an allowance, a deduction or an informational item. Payroll is built from named, individually configured components — "Basic Salary", "Transport Allowance", "Social Insurance Employee Contribution", "Loan Deduction" — rather than one monolithic calculation, so that each can carry its own rules, taxability and reporting treatment. Elements live inside one LDG and must be rebuilt per country. Every payslip line traces back to an element, and reading a client's element list is one of the first tasks on a project.

Reading that list well is a skill in itself. A well-designed element list is short, each name says what the thing is rather than what it was called in the legacy system, and the statutory elements are untouched and recognisable. A badly designed one has forty earnings elements, eleven of which are variants of "Allowance 3", and nobody left in the building knows which population each applies to. The second kind is the more common inheritance, and the first useful deliverable on a support engagement is often simply the inventory: which elements exist, who has entries for them, and which have not been used in two years.

## What the element template actually builds

Creating an element is not creating one object. The element template asks a series of questions and then generates a small family of objects, and knowing what it generated is what makes the result debuggable.

Depending on the classification, the template creates a **results element** — a nonrecurring element named for the base one with "Results" appended — that the payroll process feeds values into, taking account of frequency rules and any skip or proration formula. Answering yes to the retroactive question generates a **retro element**, also nonrecurring, named with "Retro" appended, carrying the base element's attributes with some exceptions. One of those exceptions is worth memorising, because it is quietly sensible: every retro element is given a latest entry date of final close regardless of what was chosen for the base element, so that an arrears payment can still be made to somebody who has left.

The template also creates the balances the element feeds, the balance feeds themselves, the status processing rules and the formulas that do the work. This is why two elements that look identical on screen can behave differently: they were generated by different answers to the template, and the difference lives in the objects underneath rather than on the element page.

The practical consequence for a consultant is to **answer the template carefully the first time**. Several of the questions — proration, retroactive changes, whether the element is paid separately — shape generated objects that are awkward to change afterwards. On a new implementation the right instinct is to create one element of each kind in a development environment, look at what the template produced, and only then write the configuration workbook.

## Classifications and processing priority

Each element has a **classification** — earnings, deduction, information — which controls processing order and how the element feeds balances. Payroll must process earnings before it can calculate deductions based on them, so classification drives sequencing: standard earnings, supplemental earnings, pre-statutory deductions, statutory deductions, voluntary deductions. When a calculation runs in the wrong order, classification and processing priority are the first things to check.

Underneath the classification sits a **processing priority**, a number, and the rule is that lower numbers process first. The primary classification supplies a default priority and a permitted range, and an element can be given a different number within that range. That range is the safety rail: it is not possible to drag a voluntary deduction in front of a statutory one by typing a small number, because the ranges do not overlap.

Priority matters whenever one element's result is another element's input. A loan repayment capped at a percentage of net pay has to be calculated after the things that determine net pay. A percentage-based allowance has to come after the basic salary it is a percentage of. In practice the delivered priorities are correct for the delivered elements, and the ones a consultant has to think about are the client's own elements with dependencies between them. The symptom of getting it wrong is a result that is right in the second run of a period and wrong in the first, or a value that calculates as zero because the thing it reads had not been calculated yet.

## Input values, and why they are hard to change later

An element's **input values** are the fields that hold the data the calculation needs — amount, rate, percentage, units. A "Loan Deduction" element might carry input values for total loan amount, monthly instalment and remaining balance. Deciding an element's input values is a core design decision recorded in the configuration workbook.

Each input value has a type, can be made required, and can be validated — against a range, a lookup, or a formula — and that validation is worth using. An input value that accepts any number is an input value that will one day accept 100 where 1.00 was meant.

The reason to get this right early is a restriction with real teeth: **once entries exist against an element, input values cannot be freely added or removed**. Oracle's reason is integrity — retroactive processing and the balances that read those input values depend on the shape not changing underneath them. The practical effect is that an element in production has the input values it was born with, and a client who later wants to hold one more piece of information per entry is looking at a new element and a migration of the old entries rather than a quick edit.

## Recurring, nonrecurring, and what happens at termination

An element is either **recurring** — its entry applies in every pay period until the entry is ended — or **nonrecurring**, where the entry applies to one pay period only. Salary is recurring. A one-off bonus is nonrecurring. This is one of the template answers that cannot sensibly be changed later, and it is also one that clients get wrong when describing a requirement: "they get it every month, except when they don't" is a recurring element with a skip rule or an end date, not a nonrecurring one somebody re-enters monthly.

The element's **latest entry date** decides what happens to its entries when employment ends, and the three delivered values are worth knowing by name because they are the mechanism behind "we cannot pay his final bonus".

*Last standard earning date* stops the element's entries on the date the person leaves — the ordinary case for salary and allowances, which should stop when the person stops. *Last standard process date* runs to the end of the pay period the termination falls in rather than to the termination date itself, which is the distinction people compress and then get wrong. *Final close* keeps entries open past the last day worked, which is what makes it possible to pay a bonus, a severance amount or a year-end adjustment to somebody who has already left.

Those three are the same dates Chapter 3 describes on the payroll relationship, read from the element's side: the relationship says how late the person can be processed at all, and the element's latest entry date says how late *this* element may be entered.

A vocabulary warning, because it costs an interview. Older Oracle HR — the E-Business Suite generation — called this the **termination rule** and its values *actual termination*, *final close* and *last standard process*. Those words are still in circulation, in training notes and in a great deal of material a search will surface, and they are not what Fusion calls them. If a client or a colleague says "actual termination", they mean last standard earning date.

The design conversation to have is which elements need final close, and the answer is usually a short list: end-of-service, final leave settlement, any bonus declared after the leaving date, and any statutory adjustment. Setting everything to final close instead is not a shortcut — it leaves salary entries open on leavers, and sooner or later somebody is paid for a month they did not work.

## Who can get it, and who does

Creating an element does nothing on its own. **Element eligibility** (historically "element link") defines which population the element applies to, by criteria such as payroll, legal employer, grade, job or department: "Car Allowance is eligible for grade G7 and above in the Cairo business unit." Without eligibility, an element cannot be given to anyone. This is the most common cause of "why can't I add this allowance to this employee?" — the answer is almost always that eligibility does not cover them. Eligibility defined too narrowly at build time is considerably messier to widen once entries exist.

Two design choices sit inside eligibility and both are worth making deliberately.

The first is **open versus criteria-based** eligibility. An element with no criteria is available to everyone on the payroll, and for most earnings that is the right answer — the control over who actually receives it is the entry, not the eligibility. Criteria belong where the restriction is a rule rather than a decision: an allowance that legally applies only to one legal employer, a deduction that only exists for one grade band. Encoding an HR decision as eligibility makes every exception a configuration change.

The second is **automatic entry**. An element can be configured so that an eligible person receives an entry without anyone creating one, which is how standing items like a statutory deduction attach themselves. It is powerful and it is a trap in equal measure: a change to eligibility on an element with automatic entry changes who is being paid, immediately and in bulk. Any edit to that kind of eligibility deserves the same care as a mass update.

An **element entry** is the actual attachment of an element to a specific person, with values and dates: a transport allowance of EGP 800 per month effective 1 March. Eligibility says who *could* receive something; the entry says who *does*, and how much. Entries can be created manually, loaded in bulk with HCM Data Loader (Chapter 11), or generated automatically.

## Salary, and where it actually lives

The **salary basis** decides how salary is stored, quoted and paid — annual, monthly or hourly — and which element it feeds. An annual basis stores EGP 240,000 and pays EGP 20,000 monthly. Getting the basis wrong multiplies or divides everyone's pay by twelve, so always confirm how the client quotes salary in offer letters before configuring it.

Salary is held as a dated **salary record** on the assignment, and Oracle derives the element entry from it through the salary basis. That direction matters: a raise is entered on the salary page and the entry follows, never the other way round. Editing the derived entry directly leaves the salary page and the payslip telling different stories about the same person, and nothing in the system flags the disagreement — it surfaces when somebody compares a letter to a payslip.

This is worth converting into a rule for the client's own administrators, because it is the kind of thing a well-meaning power user will do once and then teach to three colleagues. **Salary changes on the salary page. Everything else can be an entry.** An administrator who finds themselves typing a basic salary figure into an element entry has taken a wrong turn, and the earlier somebody says so the fewer records have to be unpicked.

## Salary components and the Gulf offer letter

Most Gulf offers are not quoted as one number. They are quoted as basic plus housing plus transport, and that split is what **salary components** are for: an itemised breakdown held against the salary record rather than as separate manual entries. The split is a statutory question, not a presentational one, because the contributable wage in Chapter 17 and the UAE gratuity base in Chapter 18 are both computed from particular components. Designing the components to match how the client's offer letters are written is therefore part of getting end-of-service right, and it is much harder to change afterwards than before.

The workshop question that gets to the heart of it is not "how is salary structured" but "**which part of this is the gratuity calculated on**". The answer names the components that must exist as components, and everything else can be an allowance element. Asking it that way also surfaces the disagreement that frequently exists between what the offer letter says, what the policy manual says and what payroll has actually been doing, which is a far better thing to discover in design than in parallel run.

## Rate definitions and grade rates

**Rate definitions** convert between the stored figure and the figure a process needs — an annual salary into an hourly rate for overtime, a daily rate for an absence payment, a monthly rate for a liability accrual. Grade rates, promised in Chapter 2, attach ranges or step values to grades so that pay governed by grade is validated against the band rather than typed in free. A client whose pay is individually negotiated rarely needs them; one in the public sector or a large Gulf group almost always does.

Rate definitions are the quiet dependency behind a surprising number of calculations, and they are where a hidden client policy usually lives. The hourly rate for overtime is monthly salary divided by *something*, and that something — 30 days times 8 hours, 26 days times 8, 208 hours, the actual hours in the month — is a policy choice worth several percent of the overtime bill. The same is true of the daily rate used for unpaid leave deductions and for absence payments. Each of these should appear in the design document as a named rate definition with its divisor written down, and each should be reconciled against a real legacy payslip before anyone signs it off.

## The hours side of pay

The functional track promises money, time and law, and time so far has meant leave. Hours are the other half, and they reach payroll in one of three ways: a time card in Oracle Time and Labor, an interface from a biometric or shift system, or a bulk load (Chapter 11). Choosing between them is a design decision with an owner and a cost, and it is worth making explicitly rather than discovering in the first run that attendance arrives as a spreadsheet somebody emails.

An overtime element needs two things: a rate source, which is a rate definition, and a multiplier, which is statutory rather than negotiable. Under Egypt's Labour Law 14/2025 overtime is paid at no less than 35% above the normal hourly wage for daytime hours and 70% for night hours, with total presence at the workplace capped at twelve hours a day. Saudi Arabia's Article 107 sets overtime at 150% of the hourly wage. Sources disagree on two points worth flagging rather than resolving: whether the Saudi calculation runs on basic or total wage, and whether Egyptian rest-day work is compensated as an extra day's wage plus a substitute day off or as double pay. Both were checked in 2026 and both belong in a client's written legal position before an element is built.

The design question that settles the shape is whether the client pays by the hour or by the month. An hourly salary basis fed by time cards computes pay from hours every period; a monthly salary with an overtime element computes a fixed amount plus exceptions. They produce the same payslip in an ordinary month and behave completely differently in a month with unpaid leave, a mid-month joiner or a strike of overtime claims.

There is an operational dimension that the design rarely accounts for. Time data arrives late. It arrives late every month, from a system somebody else owns, and the payroll cut-off does not move. The question to settle during design is what the payroll does when the hours are not there on the cut-off date: pay a standard figure and correct by retro, hold the person out of the run, or move the cut-off. All three are defensible; having no answer is not, and the one chosen determines how much retro the client lives with permanently.

## The calendar: payroll definitions and the cut-off

A **payroll definition** is the calendar: frequency, period start and end dates, cut-off dates and payment date — "Egypt Monthly Payroll, calendar months, cut-off on the 25th, paid on the last working day." A person must be assigned to a payroll, on the assignment, before they can be processed.

The definition generates the actual periods ahead of time, each with its dates, and those dates are what every process reads. Two of them do more work than people expect. The **cut-off** is the point after which a change will not make the current run; it is an agreement with the business rather than a lock, which is why it has to be published and defended. The **payment date** drives the bank file and, in several jurisdictions, the statutory reporting period, so moving it has consequences beyond when money lands.

The conversation worth having at design time is what happens on the edges. Where does a mid-month joiner's first period start, and are they paid a part period or held to the next one? What happens when the payment date falls on a weekend or a public holiday — and in the Gulf, where the weekend itself has moved in living memory, that question needs an answer per country rather than per group. Where a client runs several payrolls, do they share a calendar or not, and if not, what does that do to the reporting dates that follow.

## Running it

The **payroll run** (Calculate Payroll) is the engine that calculates gross-to-net for a population for a period: it evaluates elements, applies formulas, and produces run results and balances, held against the payroll relationship. Errors at this stage typically point to missing entries, missing eligibility or formula problems.

**QuickPay** runs the same calculation for a single person outside the main run — the primary testing tool during configuration (change an element, QuickPay one employee, check the result) and the mechanism for off-cycle payments such as a final settlement. A consultant who is not using QuickPay constantly during a build is working much harder than necessary: the loop of change one thing, QuickPay one person, read the result is the fastest feedback available in the product.

Which population a run covers is controlled by object groups — a payroll relationship group names a set of people, an element group names a set of elements. These are what make a targeted run possible: recalculate only the population affected by a correction, or process only the elements that changed. During parallel run and hypercare they are used constantly, and a team that does not know they exist re-runs the entire payroll to fix two people.

## Balances: the part everything else reads

A **balance** is an accumulated total of element results over a period and dimension: gross pay year-to-date, taxable earnings month-to-date. Balances have dimensions (period-, month-, quarter-, year-to-date) and scope (assignment or relationship level). Statutory calculations, payslips and reports all depend on them, and when a report shows a wrong total the balance feed is usually where the problem lives. Balances do not span payroll relationships — which is why year-to-date figures reset on a global transfer.

Three pieces of vocabulary make balance problems tractable.

A **balance feed** is what adds to or subtracts from a balance, and it can be defined in two ways: from particular element input values, or from the run results of a whole classification. The difference matters when a new element is added. An element feeding a classification-level balance joins the total automatically; an element that must feed a specific balance needs its feed created, and a missing feed is the single most common cause of "the year-to-date on the payslip is wrong but every individual line is right".

A **balance dimension** is the window and scope — the period over which the balance accumulates and whether it is held at assignment, terms or payroll relationship level. The same balance type with two dimensions is two different numbers, both correct.

A **defined balance** is the pairing of the two: a balance type plus a dimension, which is how the rest of the system refers to a balance — a gross pay balance at assignment level year-to-date, for instance, is a different defined balance from the same gross pay at relationship level. Formulas, reports and extracts all name defined balances, which is why the name looks long and why getting the dimension wrong in a formula returns a plausible number that is not the one wanted.

## Loading balances at go-live, which you only get to do once

A payroll going live in the middle of a tax year starts with a problem: year-to-date tax, insurable earnings and every other accumulated figure already exist in the old system, and the new one has to begin from them or the first payslip will be wrong in a way every employee can see.

The process is **initial balance loading**, and it has properties worth knowing well in advance.

Values are loaded into batch interface tables — through two loader files, one for the batch header and one for its lines — and then the *Load Initial Balances* process is submitted to post them. For each balance being initialised, that process defines a balance initialization element, adds it to the balance as a feed, and posts balance adjustments to set the values. Every line needs the payroll relationship number; a line initialising a terms-level balance also needs the term number, and an assignment-level one needs both term and assignment numbers — which is the model from Chapter 3 reappearing as a file format.

The dates are the control that matters. Values are set relative to an upload date, the batch header's date applies to every line unless a line overrides it, and the whole exercise depends on choosing those dates to match the point at which the legacy payroll stopped.

And then the part that makes this a one-shot exercise: **balances cannot be initialised once any payroll process has run**. After that, the only route is balance adjustments, one at a time, through an element that feeds the balance. A team that runs a test payroll in the production environment before loading balances has made a rod for its own back, and a team that discovers a wrong balance a week after go-live is doing adjustments rather than a reload.

Two smaller rules save a rehearsal each. Each balance should have exactly one initial feed. And where one element has several input values feeding balances, those balances must share an upload date.

## After the run

Calculation and payment are separate steps. **Prepayments** takes the run results and distributes them across each person's payment methods — someone may split their salary across two bank accounts. It runs after the payroll run and before the payment process, and it is the step people forget exists until a payment fails.

Payment methods come in two layers that are easy to conflate. The organization payment method is the employer's — a payment type and a source bank account, defined once. The personal payment method is the employee's — their account, and the split if they have more than one. A new joiner with no personal payment method will calculate perfectly and then fail at prepayment, which is exactly the right place for it to fail and exactly the error people misread as a payroll problem.

Oracle's standard flow then archives the results, generates payslips, and produces the payments: the **payment process** creates the bank file. In Saudi Arabia and the UAE, the file must follow the Wage Protection System SIF format (Chapter 17), and a Gulf go-live always includes a bank-file test with the actual bank. The bank file is a common cause of go-live delay; never treat it as an afterthought.

The archive step deserves more respect than it gets. The payslip is generated from archived data rather than from live records, which is both why a payslip for a past period still shows what it showed then and why a payslip that is wrong cannot be fixed by correcting the record — the archive has to be regenerated. Consultants who do not know this spend an afternoon correcting data and refreshing a payslip that will not change.

## Costing

**Costing** allocates payroll results to accounting segments so the cost lands in the right place in the general ledger, broken down by department, project or cost centre. It is the bridge between HCM and Finance and is often owned jointly with a finance consultant.

Where the cost lands is the other half of finishing a cycle. Costing is resolved segment by segment through the cost hierarchy, so one account string can be assembled from values held at several different levels. The results then reach the ledger through Transfer to Subledger Accounting and the accounting processes that follow it — Chapter 21. A costing design that is merely plausible produces a month-end reconciliation that nobody can explain, which is why the finance consultant belongs in that conversation from the start rather than at the end.

## Running it is a flow, not a button

Calculate Payroll is not a button; it is a **payroll flow** — a sequenced set of tasks with a checklist, owners and a status for each step. Submitting the flow starts it, and the checklist is where a stuck task is seen. On a real cycle the flow is what the payroll team watches, and the consultant's job in hypercare is usually reading it rather than reading a log.

The flow is also where the cycle becomes a repeatable process rather than a sequence somebody remembers. A well-built payroll cycle flow carries every step in order — retro notifications, the retro recalculation, the calculation, verification, prepayments, the archive, payslips, the payment file, costing and the transfer to accounting — with the right owner on each and a verification task where a human has to look at something before the next step runs. Building that flow with the client's payroll manager, rather than handing them a list of processes to submit, is one of the higher-value things a consultant does on an implementation, because it is the artefact the team will still be using in three years.

## Retry, roll back, and the order they unwind in

When something is wrong, three corrections do different things. **Mark for retry** flags the records that failed so the next retry picks up only those. **Retry** re-processes them after the cause is fixed. **Roll back** removes the results entirely, as though the process had not run.

The order constraint is the part to know: once prepayments have locked a run's results, the run cannot be rolled back until the prepayments are rolled back first. Corrections therefore unwind in the reverse of the order they were made, and a team that tries to roll back a run with prepayments sitting on top of it gets an error that reads like a bug and is not.

The same logic extends along the whole chain, and it is worth picturing as a stack. Costing sits on payments, payments sit on prepayments, prepayments sit on the run. Anything resting on top of the thing being removed must come off first. The practical rule during hypercare is to establish how far down the stack a correction has to reach *before* starting, because a half-unwound cycle at eight in the evening is where mistakes are made.

The other practical rule is to prefer retry over roll back where both would work. Retry is narrower, faster, and leaves the rest of the run untouched; rolling back a whole payroll to fix four people is a blunt instrument that creates its own risks.

## The quiet failures

The failures worth rehearsing are the quiet ones. A person not assigned to a payroll is skipped by the run without an error. A salary basis that says monthly while the annual figure was loaded against it pays twelve times the intended salary, and the run reports nothing, because it calculated exactly what it was given. A deduction classified as an earning is added to gross instead of taken off it. None of these produce a failure message; all of them produce a payslip.

The defence against this class of problem is not more careful configuration — it is a set of checks that run every cycle and are read by somebody. The useful ones are cheap: the headcount in the run against the headcount expected, the total gross against last period with the difference explained, a list of anybody whose net pay moved by more than a threshold, a list of anybody in the population who was not processed, and a check that nobody's net pay is negative or implausibly large. Four of those five are simple reports, and together they catch nearly everything that otherwise reaches an employee's bank account.

## Proving it works: the parallel run

A **parallel run** executes the new system's payroll alongside the legacy payroll for the same period and reconciles the two line by line. It is the only reliable proof that the new payroll is correct before the old one is switched off, and it typically runs for two or three consecutive months before go-live. Differences must be explained, not just noted. It is also the highest-stakes activity before go-live, and the point where a consultant with analytical instincts is visibly useful.

Two habits separate a reconciliation that proves something from one that merely documents. The first is reading every line rather than the exceptions someone has already flagged, because a difference nobody noticed is exactly the one that reaches hypercare. The second is remembering what the exercise can and cannot prove: a matching line proves the new system agrees with the old one, not that either agrees with the client's policy. Where legacy is wrong — an out-of-date insurable-wage ceiling, an allowance paid flat that policy says is a percentage — the correct outcome is a difference, raised with the client rather than configured away.

It is worth structuring the reconciliation rather than improvising it. Compare at three levels: the control total for the whole population, the total per element, and then the individual people whose totals differ. Most differences cluster — twenty people differ by the same amount for the same reason — so the per-element layer finds causes much faster than a person-by-person scan. Every difference gets one of four dispositions: the new system is wrong and will be fixed, the legacy system is wrong and the client accepts it, the two are both right and the difference is a deliberate policy change, or the difference is a rounding treatment that has to be documented. A parallel run signed off without a difference log is not signed off; it is just finished.

The second and third cycles matter as much as the first. The first parallel run finds configuration errors. The second finds the things that only happen in some months — a quarterly payment, a joiner, a leaver, a retro. The third proves the team can do it, which is the part that actually determines whether go-live is calm.

## Hypercare and the first live run

Go-live is not the finish line; the first live payroll is, and the two are usually a few weeks apart.

The things that go wrong in the first live run are rarely the things tested hardest. They are the operational edges: a time file that arrived in a different format, a bank that rejected the file for a reason the test file never triggered, a joiner created after cut-off, a leaver whose final settlement needed an element whose latest entry date stopped at the last standard earning date. Planning for hypercare means planning for the day of the run rather than for the configuration — who is in the room, who can approve an exception, how late the payment can be submitted and still land on time, and what the fallback is if the file is rejected.

The one piece of advice that pays for itself: run the entire cycle in a non-production environment with production-like data one week before the first live run, timed. Not a test of the configuration, which has been tested, but a rehearsal of the day. It finds the things nobody wrote down.

## Common mistakes

- Creating an element and expecting it to appear on payslips. Nothing happens until eligibility exists and an entry is made.
- Confusing eligibility (who could) with entry (who does).
- Answering the element template carelessly, then discovering the generated objects cannot be changed.
- Designing input values loosely, then finding they cannot be added once entries exist.
- Setting every element's latest entry date to final close, and paying leavers for months they did not work.
- Saying "termination rule" and "actual termination" in a Fusion conversation. Those are the previous generation's names.
- Encoding an HR decision as element eligibility, so every exception becomes a configuration change.
- Editing a derived salary element entry instead of the salary record.
- Leaving the overtime divisor undocumented, then being unable to explain an hourly rate.
- Forgetting a balance feed for a new element, and seeing correct lines with a wrong year-to-date.
- Confusing two dimensions of the same balance, in a formula or in a report.
- Running a payroll process in production before initial balances are loaded, and losing the ability to load them.
- Forgetting prepayments sits between calculation and payment.
- Correcting a record to fix a payslip, without regenerating the archive.
- Trying to roll back a run with prepayments still on top of it.
- Rolling back a whole payroll to fix four people.
- Treating the bank file as a formality.
- Signing off a parallel run without a difference log.
- Believing go-live means done. Hypercare and the first live payroll are the finish line.
